  # Separate Express Backend with LTS and TDD

  ## Summary

  Convert PG Manager Pro into a monorepo containing independently deployable web, API, and worker applications:

  PG Manager Pro/
  ├── apps/
  │   ├── web/        existing TanStack React frontend
  │   ├── api/        Express 5 REST API
  │   └── worker/     BullMQ background jobs
  ├── packages/
  │   ├── contracts/  Zod schemas, OpenAPI definitions, generated client
  │   ├── db/         Drizzle schema, migrations, repositories
  │   ├── config/     shared TypeScript, ESLint and environment configuration
  │   └── test-utils/ PostgreSQL, Redis and fixture helpers
  └── pnpm-workspace.yaml

  Target stack:

  - Node.js 24 LTS and TypeScript
  - Express 5
  - Neon PostgreSQL with Drizzle
  - Better Auth
  - Redis and BullMQ
  - S3-compatible storage, using R2/S3 in production and MinIO in tests
  - Pino structured logging
  - Zod validation and OpenAPI
  - Vitest, Supertest, Testcontainers and Playwright smoke tests
  - pnpm workspaces

  ## Implementation Changes

  ### Backend foundation

  - Create an Express application factory separate from the network listener so tests can instantiate the API without opening ports.
  - Organize each module as route/controller → application service → domain rules → repository/provider adapter.
  - Prevent controllers from directly accessing Drizzle, Redis, storage, email or payment providers.
  - Add Helmet, exact-origin credentialed CORS, rate limiting, request IDs, Pino HTTP logging, centralized error handling and graceful
    shutdown.

  - Expose /health/live, /health/ready and version/build information.
  - Validate environment variables at startup and fail without printing secret values.
  - Run the API and BullMQ worker as separate processes and deployment units.

  ### API and authentication

  - Expose versioned REST endpoints under /api/v1; mount Better Auth under /api/auth.
  - Generate OpenAPI from shared Zod contracts and generate the frontend TypeScript client from that specification.
  - Use secure HttpOnly cookies, trusted frontend origins, CSRF protection and exact subdomain configuration.
  - Model authorization around workspaces and workspace_memberships, even while each workspace initially has one owner.
  - Keep platform administrators separate from owner memberships and require newly enrolled MFA before console access.
  - Return consistent RFC 9457 problem responses with a request ID.
  - Require idempotency keys for billing runs, payment mutations, notification jobs and payment webhooks.

  ### Data and background work

  - Move all database access behind the Express API; the final frontend must contain no Supabase service/database calls.
  - Put workspace_id on tenant-owned records and enforce tenant/property/room relationships, nonnegative amounts and uniqueness in PostgreSQL.
  - Make payment-ledger aggregation, plan activation and billing transitions transactional.
  - Use an outbox table plus BullMQ for bill generation, email/WhatsApp delivery, reminders and backup jobs.
  - Make every job retry-safe using database uniqueness keys rather than only pre-send queries.
  - Retain Resend and Razorpay behind provider interfaces; use the official Meta WhatsApp API if WhatsApp is implemented.
  - Store private KYC objects under workspace-scoped keys and issue short-lived signed URLs after authorization.
  - Add Neon backups/PITR plus scheduled logical exports to S3-compatible storage and documented restore drills.

  ### Incremental migration

  1. Move the existing frontend into apps/web without changing behavior and establish shared tooling and CI.
  2. Add characterization tests for current auth, tenant isolation, billing, payments and reminders.
  3. Introduce Express as an API facade over the current Supabase PostgreSQL database and Supabase Auth. Migrate modules in this order:
      - identity and workspace authorization;
      - properties, rooms and tenants;
      - KYC documents and readings;
      - bills and payments;
      - reports and settings;
      - jobs and notifications;
      - plans and platform console.

  4. Put each frontend module behind a feature flag. Compare legacy and API reads, switch writes after integration tests pass, and retain a
     rollback flag.

  5. After all browser database access is removed, rehearse and perform the Supabase PostgreSQL → Neon migration with record counts, monetary
     totals, relationship checks and object checksums.

  6. Import Supabase identities into Better Auth without passwords. Send expiring, single-use activation links requiring owners to set a new
     password; require platform administrators to re-enrol MFA.

  7. Copy KYC objects to S3-compatible storage, verify checksums, then switch signed-URL generation.
  8. Perform the final data/auth/storage cutover during a brief write freeze, validate reconciliation, enable the new services and retain the
     legacy system read-only for the rollback window.

  9. Remove Supabase clients, server functions and migrations only after the rollback window and production verification finish.

  ## TDD and Verification

  Add a dedicated TDD policy section to data-points/project.md stating:

  - Strict red-green-refactor applies to all new backend behavior.
  - Start with a failing behavior test before adding production logic.
  - Migrated behavior requires a characterization test before refactoring.
  - Unit tests cover domain calculations and authorization decisions.
  - Supertest integration tests cover every REST endpoint and error contract.
  - Testcontainers runs real PostgreSQL migrations and Redis/BullMQ behavior.
  - Contract tests fail when OpenAPI and the generated frontend client drift.
  - Critical Playwright smoke tests cover owner activation, tenant creation, bill generation, payment recording and cross-owner denial.
  - Bug fixes require a regression test that fails before the fix.
  - CI blocks merging unless formatting, lint, typecheck, tests, migration checks, OpenAPI generation and builds pass.
  - Minimum backend coverage is 80% for lines, statements, functions and branches, with at least 90% branch coverage for auth, billing,
    payments and job-idempotency modules.

  - Frontend-wide strict TDD is not included initially; frontend changes require contract tests and critical smoke coverage.

  Required scenarios include:

  - Cross-owner access is rejected for every resource and privileged job.
  - Repeated or concurrent billing requests create one tenant-month bill.
  - Concurrent reminder workers produce one notification.
  - Payment and plan failures roll back completely and retry safely.
  - Overpayment and invalid tenant/property relationships are rejected.
  - Activation links are single-use and expire.
  - Signed KYC URLs cannot cross workspace boundaries.
  - Migration rehearsals preserve record counts, financial totals and object hashes.
  - API or worker shutdown does not lose accepted jobs.

  ## LTS Assumptions

  - Express 5 replaces Fastify.
  - The backend remains a modular monolith; do not split it into microservices.
  - Web, API and worker share one Git repository but deploy independently.
  - Node stays on an LTS major, with scheduled annual major upgrades and automated dependency update PRs.
  - REST /api/v1 remains backward-compatible; breaking changes require a new API version and a documented deprecation window.
  - Database changes use forward-only, backward-compatible expand/migrate/contract migrations.
  - Existing accounts, operational records, billing history and KYC documents must be preserved.
  - data-points remains outside Git; only application changes are committed.
