# PGKhata V1 — Build Log (2026-09-03)

## Scope

This release completes the meter-reading billing workflow, invoice clarity, property navigation, and repository cleanup requested during the September 3 session.

## Electricity and Billing

- Meter billing uses a reading pair per room: an opening reading and the next closing reading.
- The billed units are `closing reading - opening reading`; the first reading only establishes the baseline and bills zero units.
- The closing reading date determines the billable period, so a bill generated late still uses the actual meter-reading dates.
- A tenant who joins during that period receives a day-based share of the room electricity cost for the days they stayed.
- Bills store electricity line-item metadata: room meter units and the configured per-unit rate. The invoice renders these as, for example, `352 units` and `₹12/unit`.
- New invoices are due five calendar days after their issue timestamp. A bill issued on 3 September is due on 8 September.
- Existing invoices are snapshots: delete and regenerate an old invoice to apply newly calculated electricity or due-date values.

- Added Edit and Delete controls on the main Meter Reading page.
- Editing validates chronological position and prevents readings from breaking the room meter sequence.
- Deleting or editing a reading recalculates the immediately following reading’s unit difference.

## Security Hardening

### Platform Admin Table

- Added `platform_admin` table with `user_id` foreign key (unique, cascade delete).
- Migration `0018_add_platform_admin.sql` creates the table.
- The `requireSuperAdmin` middleware now queries this table to verify the authenticated user is a platform admin.
- Returns 403 "Platform admin access required" for non-admin users.
- Previously, the middleware was a no-op that passed all authenticated users through.

### Workspace-Scoping Tests

- New test file: `workspace-scoping.integration.test.ts`
- Creates two isolated owners (Owner A and Owner B) with separate properties, rooms, tenants, and bills.
- Tests prove:
  - Owner A's properties are isolated from Owner B
  - Owner A's tenants are isolated from Owner B
  - Owner A's bills are isolated from Owner B
  - Database allows cross-tenant inserts without RLS (documents the risk)
- Tests run only when DATABASE_URL is present (integration tests).

### Payment Idempotency

- Added `idempotency_key` text column to `payment` table.
- Partial unique index `payment_bill_idempotency_uq` on `(bill_id, idempotency_key)` where key is not null.
- Migration `0019_add_payment_idempotency.sql` adds the column and index.
- Payment recording API now checks for existing payment with same idempotency key before inserting.
- Returns 200 "Payment already recorded" if duplicate key detected.
- Frontend generates idempotency key as `{billId}-{amount}-{paymentDate}-{timestamp}`.
- Prevents duplicate payments from double-clicks or network retries.
