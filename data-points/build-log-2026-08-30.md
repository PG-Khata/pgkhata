### 2. Design System

Applied a non-generic, handcrafted design philosophy based on research into Linear, Khatabook, Zoho, Notion, and Vercel dashboards.

**Key decisions:**
- Dense information layout (text-sm default, compact tables)
- Borders over shadows (no shadow-heavy cards)
- Monochrome base + semantic color accents (emerald/amber/red for status)
- Typography hierarchy (font-weight/size, not decorative elements)
- Geist Mono for amounts (₹12,000), room numbers, phone numbers
- Indian rupee formatting: `Intl.NumberFormat('en-IN')` → ₹2,42,000
- Status badges: muted bg + colored text (bg-emerald-50 text-emerald-700)
- No emoji in navigation, no gradient CTAs, no "Welcome back" greetings
- Mobile-first: bottom nav with 4 items + "More" drawer
- Sidebar: w-56 (compact), text-only nav items

**shadcn/ui configuration:**
- Style: base-nova (Default, not New York)
- Base color: neutral (Zinc)
- CSS variables for theming
- Radius: 0.625rem (not rounded-xl everywhere)

### Recurring issues found and fixed along the way

- **Authorization holes retrofitted twice**: `bills/approve` (found during Task 9) and `payments/:id DELETE` (found during Task 11) both had zero ownership checks before this session — any authenticated owner could act on any other owner's records by id. Both fixed with an ownership join before the mutation.
- **Test-cleanup script drift**: `packages/db/scripts/cleanup-test-data.ts` fell behind the schema repeatedly as new tables were added (Tasks 9, 10, 12) — it kept scoping deletes through `room.propertyId` joins that miss tenants/records created without a room, and never deleted new tables (`advance_payment`, `security_deposit`) at all until each task's teardown crash forced a fix. Now scopes tenant/bill/deposit/expense deletion directly by `property_id` everywhere.
- **Drizzle error-cause chain**: Postgres SQLSTATE codes live on `error.cause`, not on the caught error directly, because drizzle wraps driver errors. This tripped up both `security-deposits.ts` and `expenses.ts` on first pass (silently fell through to 500 instead of returning 409) until fixed with a `pgErrorCode()` helper that walks the cause chain — mirrors a pattern the test suite's own `pg-error.ts` helper already used for assertions.
- **Stale test assumptions on shipped features**: `mobile-nav.test.tsx` hardcoded "Expenses" as the example of a disabled/upcoming nav item; broke the moment Task 13 shipped it. `bed-assignment.integration.test.ts` asserted the OLD signup-immediately-assigns-a-bed behavior; broke the moment Task 14 changed it. Both were intentional behavior changes, not regressions — fixed by repointing the assertions at what the new behavior actually is, not by reverting the feature.

### Known gaps not covered by this 16-task plan (need a decision, not silently dropped)

1. **`useApplyAdvancePayment` has no UI** (Task 11). The hook exists; no page or button calls it. Applying an advance to a specific bill currently requires a direct API call. Natural next spot: an "Apply advance" action on the tenant detail page or next to a bill's balance in `billing/page.tsx`.
2. **`bill.promisedDate` was never built** (`missing-features.md` #18, MEDIUM priority, explicitly deferred at Task 10). Promised-payment-date suspension of late fees is not implemented. Note this is distinct from `security_deposit.promisedDate`, which **was** built (Task 12) — different feature, same word.
3. **`/dashboard/payments` remains flagged `upcoming: true`** in `nav-config.ts`. It was never owned by any of the 16 tasks and needs an explicit decision: build it as its own task, or intentionally leave the nav item disabled and document that.
4. **Manually-added tenants skip the approval workflow.** Task 14 gated the *public signup* path behind pending/approve/reject; a tenant the owner adds directly via the regular form still defaults straight to `active`. This matches `missing-features.md` #9's own "what to build" section (which only describes gating signup), but Niketan's item description mentions "signup or manual entry" generically, so the two products may diverge here intentionally or not — flagging for the user's call.
