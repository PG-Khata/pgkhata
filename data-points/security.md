# PGKhata security

Last verified against source: 2026-08-03

Every finding below was read in the current source and then independently
re-checked by a second reviewer instructed to default to "not confirmed."
Claims that could not be grounded in a real file were dropped. Findings are
ordered by exploitability, not by how alarming they sound.

Scope: `PG Manager Pro/` — `apps/web` (legacy, live), `apps/api` and
`apps/worker` (new, partial).

---

## Critical

### S-1. Any owner can run billing for every other owner

**Status: Verified. Live cross-tenant defect.**

`apps/web/src/lib/billing-run.functions.ts`

```ts
export const generateMonthlyBills = createServerFn({ method: "POST" })
  .middleware([requireSupabaseAuth])          // any authenticated owner
  .handler(async ({ data }) => {
    const { runMonthlyBilling } = await import("@/lib/billing-run.server");
    return runMonthlyBilling(data.month);      // no ownership argument
  });
```

`apps/web/src/lib/billing-run.server.ts` then opens a service-role client,
which bypasses row-level security entirely, and queries with no ownership
predicate:

```ts
const supabase = createClient<Database>(
  process.env["SUPABASE_URL"]!,
  process.env["SUPABASE_SERVICE_ROLE_KEY"]!, ...);

supabase.from("admins").select("id")           // every admin
supabase.from("tenants").select("id, room_id, monthly_rent_override, status")
```

**Impact.** Any owner with a valid session can generate bills across every
account on the platform, and the returned `BillingRunResult` leaks cross-tenant
counts and error strings.

**Fix.** The job is platform-wide by design; the entry point is not. Either
require `assertPlatformAdmin`, or pass the authenticated admin id down and
scope every query to it. Add a cross-owner authorization test that fails
before the fix.

### S-2. Any owner can email every other owner's tenants

**Status: Verified. Live cross-tenant defect, with side effects.**

`sendPaymentReminders` in `apps/web/src/lib/reminders.functions.ts` has the
identical shape, and `apps/web/src/lib/reminders.server.ts` uses the same
service-role escape hatch:

```ts
function serviceClient() {
  return createClient<Database>(process.env["SUPABASE_URL"]!,
    process.env["SUPABASE_SERVICE_ROLE_KEY"]!, ...);
}
...
await supabase.from("bills").update({ status: "overdue" }).in("id", overdueToMark);
```

**This is worse than S-1 because it is not read-only.** It dispatches real
email to other owners' tenants through Resend, and mutates their bills to
`status='overdue'`. The damage is external and not undoable — a tenant who
receives a spurious overdue notice has received it.

**Fix.** Same as S-1, and treat this one as the higher priority of the pair.

### S-3. A live API key is committed in migration SQL, and the cron it
authenticates has never worked

**Status: Verified. Two defects in one file.**

`apps/web/supabase/migrations/20260801202733_64411508-e536-4642-be97-1826ef5b52b3.sql`

```sql
SELECT cron.schedule('generate-monthly-bills', '0 6 1 * *', $$
  SELECT extensions.http_post(
    url := 'https://basera.app/api/public/hooks/generate-bills',
    headers := '{"Content-Type": "application/json",
                 "apikey": "sb_publishable_ZuBwZ0dGleq9eCE0WZtT3g_Wclo4yB-"}'::jsonb,
    body := '{}'::jsonb) as request_id;
$$);
```

The route it calls accepts something entirely different
(`apps/web/src/routes/api/public/hooks/generate-bills.ts`):

```ts
const provided = request.headers.get("x-cron-secret")
  ?? request.headers.get("authorization")?.replace(/^Bearer\s+/i, "");
if (!expected || !provided || provided !== expected) {
  return new Response("Unauthorized", { status: 401 });
}
```

Three consequences:

1. **Scheduled billing has been silently 401-ing since deployment.** No monthly
   bills have ever been generated by the cron. Nothing alerts on this.
2. **A publishable key is in committed source**, along with a hardcoded
   `basera.app` URL and project configuration.
3. **There is no reminder cron at all.** Across all 21 migrations,
   `cron.schedule` appears twice, both for `generate-monthly-bills`. The
   `send-reminders` hook is unreachable by any scheduler, despite the pricing
   page advertising scheduled daily reminders.

**Fix.** Rotate the key. Store the hook secret in Supabase Vault or an
equivalent rather than inline SQL. Align the header contract. Parameterize the
URL. Add the missing reminder schedule and verify both end to end after
deploy — a scheduled job with no success signal is indistinguishable from one
that never runs.

Secondary: both hooks compare the secret with `!==` rather than a timing-safe
comparison. Low severity for a high-entropy secret, but free to fix.

## High

### S-4. Bill row-level security does not prove the tenant belongs to the property

**Status: Verified. No database backstop.**

`apps/web/supabase/migrations/20260801224354_4175762e-5e92-4465-bd40-c32e247bf646.sql`

```sql
CREATE POLICY bills_own ON public.bills FOR ALL TO authenticated
  USING (private.owns_property(property_id))
  WITH CHECK (private.owns_property(property_id));
```

The policy checks only `property_id`. An owner can insert a bill carrying
another owner's `tenant_id` as long as `property_id` is one of their own, and
`WITH CHECK` is satisfied. The `bills` table has foreign keys to both `tenants`
and `properties` but no composite constraint or trigger tying them together, so
the schema does not compensate.

**Fix.** Extend the policy to require ownership of the tenant as well, and add
a database-level constraint or trigger enforcing that `bills.tenant_id`
resolves through `rooms` to `bills.property_id`.

### S-5. Razorpay upgrades apply on a client-supplied signature alone

**Status: Verified. No provider verification, no webhook.**

`apps/web/src/lib/plan.functions.ts` verifies the HMAC and immediately grants
the plan. `apps/web/src/lib/plan-checkout.server.ts` exports only
`createRazorpayOrder` and `verifyRazorpaySignature` — there is no
payment-fetch helper anywhere in the module.

The signature proves that `order_id|payment_id` were signed. It does **not**
prove money moved, that the payment was captured rather than merely authorized,
or that the captured amount equals the invoiced amount.

Compounding it: the entire web app has exactly two API route files, both cron
hooks. **There is no Razorpay webhook endpoint.** Confirmation depends entirely
on the browser calling back. A user whose browser closes after a successful
payment is charged, left on the old plan, with `plan_payments` stuck at status
`created` and no reconciliation path.

**Fix.** Fetch `GET /payments/{id}` and assert `status === "captured"` and
amount equality before granting. Add a webhook as the authoritative source of
payment state. Enforce uniqueness on provider payment ids.

### S-6. Platform login-attempt endpoints are unauthenticated — and the lockout
they implement is advisory anyway

**Status: Verified. Cuts both ways.**

`apps/web/src/lib/platform-auth.functions.ts` — `notePlatformLogin` and
`getPlatformLockout` carry no `.middleware([requireSupabaseAuth])` and write to
`super_admin_login_attempts` through the service-role client. Anyone can insert
unlimited failed attempts for the platform admin email, or probe lockout state.

But the more important half is the reverse. `apps/web/src/components/platform-auth-gates.tsx`:

```ts
const pre = await lockoutFn({ data: { email } });
if (pre.locked) { setLocked(true); throw new Error(...) }
const { error } = await supabase.auth.signInWithPassword({ email, password });
```

The lockout is a client-side pre-check. An attacker skips the React form and
brute-forces Supabase Auth directly, with zero throttling from this code. So
the unauthenticated endpoint cannot actually lock a real admin out — it can
only corrupt the attempt record — and the lockout is not a security boundary in
the first place.

**Fix.** Require authentication on the recording endpoint to stop audit
poisoning, and move rate limiting to where authentication actually happens
rather than in front of it.

## Medium

### S-7. Email HTML is built by unescaped interpolation

**Status: Verified. No escaping helper exists in the codebase.**

`apps/web/src/lib/reminder-message.ts` and `apps/web/src/lib/email.server.ts`
both interpolate directly:

```ts
<p style="...">${d.propertyName} — Room ${d.roomNumber} — ${d.monthLabel}</p>
<p style="...">Hi ${d.tenantName},</p>
```

A grep for escaping utilities across `src/lib` returns only a CSV quote-doubler
in `billing.ts`, unrelated to HTML. An owner who names a property with markup
gets it rendered in every tenant's mail client — a stored injection into
outbound mail, usable for phishing under the owner's brand.

**Fix.** One escaping helper applied to every interpolated value. This is a
small function and there is no reason to defer it.

### S-8. Tenant phone is globally unique across all owners

**Status: Verified in legacy. Already fixed in the new schema.**

`apps/web/supabase/migrations/20260801162455_*.sql` declares `phone TEXT NOT NULL UNIQUE`
with no admin scoping. Owner A cannot register a tenant whose phone Owner B
already used. That is both a cross-tenant existence oracle — probe a phone,
infer registration elsewhere — and a denial-of-registration vector.

`packages/db/src/schema.ts` already scopes it correctly:

```ts
uniqueIndex("tenants_workspace_phone_uq").on(table.workspaceId, table.phone)
```

**Fix.** Scope the legacy constraint per admin, or accept it until the tenants
module migrates. Do not let it survive the migration.

## Controls that already exist

These are real and must survive the migration. Removing one during a refactor
would be a regression, so they are listed explicitly.

| Control | Where |
| --- | --- |
| CSRF middleware, deliberately re-registered for server functions | `apps/web/src/start.ts` |
| Bearer claim verification via `supabase.auth.getClaims()`, not client-side decode | `apps/web/src/integrations/supabase/auth-middleware.ts` |
| RLS enabled on all 17 legacy tables, `USING` and `WITH CHECK` on both sides | `20260801162455_*.sql` |
| Ownership helpers moved to a `private` schema REVOKEd from anon/authenticated, `SECURITY DEFINER` with pinned `search_path`, public copies dropped | `20260801224354_*.sql` |
| Server-enforced AAL2 — platform actions require a live non-disabled `super_admins` row **and** an `aal2` session | `apps/web/src/lib/platform-auth.server.ts` |
| Append-only audit log via a `BEFORE UPDATE OR DELETE` trigger that raises unconditionally; service_role granted only SELECT+INSERT | `20260802163404_*.sql` |
| Mandatory written reason (min 4 chars) on manual plan overrides, stored in the audit log | `apps/web/src/lib/super-admin.functions.ts` |
| Constant-time, length-guarded signature comparison | `apps/web/src/lib/plan-checkout.server.ts` |
| Service-role client behind a lazy Proxy in a `.server.ts` module, to keep it out of the client bundle | `apps/web/src/integrations/supabase/client.server.ts` |
| Storage RLS scoped by `auth.uid()` as the first path segment; uploads to `${userId}/uuid.ext`, reads via short-lived signed URLs | `20260801162545_*.sql` |
| `.env` and `.env.*` gitignored with an explicit credential warning; the local `.env` holds only publishable values | `.gitignore` |

One clarification worth recording: `PLATFORM_EMAILS` in `platform-auth.server.ts`
is exported but never read by `assertPlatformAdmin` or `loadIdentity`. It is
dead code, not a control. Actual gating is the `super_admins` table row, which
is the correct mechanism.

Similarly, `adminExists` in `admin-setup.functions.ts` is an unauthenticated
service-role function, but it leaks only a boolean and is needed to bootstrap
the first account. A deliberate, bounded exception rather than a finding.

## New backend posture

`apps/api` is materially better structured than the legacy app. It is also
young enough that its gaps are cheap to close now.

### Present

- `apps/api/src/app.ts` — helmet, `x-powered-by` disabled, `trust proxy` pinned
  to 1 (correct for a single reverse proxy; avoids rate-limiter IP spoofing),
  single-origin credentialed CORS, 1 MB JSON body cap, 120 req/min limiter.
- `apps/api/src/auth.ts` — Better Auth with `requireEmailVerification`, secure
  cookies in production, one trusted origin, five-minute session cookie cache.
- `packages/config/src/index.ts` — Zod env validation at boot;
  `BETTER_AUTH_SECRET` must be at least 32 characters. The process fails fast
  rather than starting with a weak secret.
- `apps/api/src/modules/properties/repository.ts` — tenancy enforced at the
  repository layer. Routes never read a workspace id from the request body.
- `packages/storage/src/index.ts` — `workspaces/<id>/` key prefix, `..`
  rejected, AES256 at rest, signed-URL TTL capped at 900s via `Math.min`
  regardless of caller input.
- `apps/api/src/errors.ts` — no stack traces leak; unknown errors return a
  generic message and log server-side.
- `packages/config/src/logger.ts` — authorization headers, cookies, set-cookie,
  and fields named password/token/secret are redacted.

### Gaps to close

**N-1. No RLS in the new schema.** `packages/db/src/schema.ts` defines no
policies and never enables row-level security. Tenancy is application-code
only. A single forgotten `where` clause in a future repository is a full
cross-tenant leak with no database backstop — precisely the protection the
legacy system had. Add RLS, or add a mandatory workspace-scoping test to every
repository. Preferably both.

**N-2. Non-deterministic workspace binding.** `apps/api/src/auth.ts`:

```ts
const [membership] = await db.select().from(workspaceMemberships)
  .where(eq(workspaceMemberships.userId, session.user.id)).limit(1);
```

No ordering, no way for a client to request a specific workspace. The schema
already permits multi-membership via a composite primary key. This becomes a
cross-tenant access bug the moment a user belongs to two workspaces.

**N-3. Role is carried but never enforced.** `Identity` includes
`role: "owner" | "manager"`, but `requireIdentity` only checks that an identity
exists. There is no authorization middleware — every route is reachable by any
member regardless of role.

**N-4. No per-route limit on credential endpoints.** Better Auth is mounted in
`server.ts` after `createApp` returns, so it sits behind the global 120/min
limiter. 120 password attempts per minute per IP is generous for a login
endpoint.

**N-5. Redaction is literal-path only.** pino redact paths are not substring
matches, so `accessToken`, `apiKey`, `client_secret`, or a nested
`req.body.user.password` are logged in the clear. `DATABASE_URL` and
`REDIS_URL` embed credentials and are not in the list at all.

## Secrets hygiene

The committed publishable key in S-3 is the worked example. The rules that
follow from it:

1. **No secret in migration SQL.** Migrations are committed, diffed, and
   copied into chat transcripts. Use a secret store and reference it.
2. **No environment-specific URL in migration SQL.** `basera.app` is hardcoded
   in three places; when the domain changes, the cron silently targets nothing.
3. **Rotate on exposure, do not reason about severity.** A publishable key is
   lower-impact than a service-role key, but the correct response to "a key is
   in source" is rotation, not classification.
4. **Never paste `.env` contents, service-role keys, or tokens into AI chats
   or into `data-points`.** This is already the rule in `AI-work-log.md`.
5. **Verify what is staged before committing.** The current `.gitignore` is
   correct; the risk is a new file that does not match its patterns.

## Order of work

This ordering is the input to `phases.md`. It is exploitability-first, with
one exception: the test harness comes second, because fixing authorization
without a cross-owner test that fails first is how a fix silently regresses.

1. S-1, S-2 — scope or platform-gate the two service-role entry points.
2. Cross-owner authorization test matrix (see `phases.md` Phase 1).
3. S-3 — rotate the key, align cron authentication, add the reminder schedule,
   verify both schedules fire in a deployed environment.
4. S-4 — bill tenant/property consistency in both the policy and the schema.
5. S-5 — Razorpay provider verification and webhook.
6. S-6, S-7, S-8 — lockout boundary, HTML escaping, phone scoping.
7. N-1 through N-5 — close the new backend gaps before more modules migrate,
   while there is only one module to retrofit.
